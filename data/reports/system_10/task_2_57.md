# Balancing Data Security and Interoperability in Open Banking API Standards: An Analysis of OAuth 2.0 Token Management and Permission Leakage Risks

Open banking has emerged as a transformative force in financial services, enabling seamless data sharing between financial institutions and third-party providers through standardized application programming interfaces (APIs). However, this interconnected ecosystem introduces a fundamental tension between two critical objectives: enabling broad interoperability across diverse platforms and maintaining robust protection of sensitive financial data. This report examines whether current open banking API standards, particularly those built on OAuth 2.0, successfully balance these competing demands or whether token management practices inherently increase permission leakage risks. The analysis reveals that while modern standards like FAPI 2.0 and OAuth 2.1 represent significant security improvements, implementation gaps, scope creep vulnerabilities, and token management challenges continue to create substantial risks that can compromise the security benefits intended by standardization. Current evidence suggests that without disciplined governance and context-aware security controls, the interoperability gains of open banking come at the cost of expanded attack surfaces and persistent permission leakage vulnerabilities that affect both institutional and consumer security.

## The Architecture and Purpose of Open Banking API Standards

Open banking fundamentally reimagines financial data access through standardized, secure channels rather than proprietary integrations. The concept of interoperability, defined as the ability for a system to work seamlessly with another system, sits at the very heart of open banking's value proposition[1]. Interoperability in this context means that financial data flows easily and securely between data providers—typically banks and credit unions—and third-party data recipients such as fintechs and other providers of financial products and services[1]. This standardized approach removes traditional barriers between different financial entities, creating what advocates describe as fostering innovation and enhancing the customer experience[1].

The move toward open banking APIs represents a deliberate departure from earlier data-sharing methods. Approximately twenty years ago, when the financial data-sharing ecosystem first emerged, financial institutions and fintechs relied almost entirely on screen scraping to pull data from other financial providers into their own systems[1]. This practice, while useful at its inception, proved far less secure, less reliable, and less standardized than modern API-based approaches[1]. Screen scraping also placed enormous burdens on developers and organizations to manage the technical complexity and cost of maintaining tens of thousands of data endpoints[1]. By contrast, open banking APIs streamline this process significantly by standardizing data sharing through a centralized portal that manages data providers' systems[1].

The regulatory impetus for open banking standards emerged from recognition that proprietary data silos created inefficiencies and limited consumer choice. In Europe, the revised Payment Services Directive (PSD2) mandated that banks provide third-party access to consumer banking, transaction, and other financial data through APIs after obtaining consumer consent[54]. The United Kingdom established its own specific set of open banking regulations similar to PSD2, managed by the Open Banking Implementation Entity (OBIE), which implemented a more structured approach aimed at standardizing how banks and third parties interact[54]. In the United States, the Consumer Financial Protection Bureau (CFPB) has promoted digital interfaces to foster secure, authorized data-sharing between financial institutions and third-party applications[31]. These regulatory frameworks reflect a consensus that standardized APIs represent the superior approach to facilitating financial innovation while managing risks.

Standard-setting organizations like the Financial Data Exchange (FDX) have been instrumental in driving consistency and efficiencies across the ecosystem by establishing clear technical standards that keep data flowing effectively and securely for consumers and businesses[1]. These standards provide the technical foundation upon which modern open banking ecosystems operate, defining protocols, data formats, authentication mechanisms, and security requirements that banks and third-party providers must implement. The existence of these standards is intended to reduce implementation variability and create a common security baseline across the industry.

## OAuth 2.0 as the Foundation of Open Banking Security

OAuth 2.0 has become the dominant authorization framework for open banking APIs, providing mechanisms for secure token-based access without exposing user credentials. The protocol enables third-party applications to access user data by obtaining tokens that grant limited, time-bounded access to specific resources[4]. When a customer interacts with a third-party provider offering financial services, they typically authorize the TPP to access their data through an OAuth process, logging in to their bank account and granting the TPP permission to access their information[4]. This process ensures that the TPP has consent to access the data while maintaining the customer's privacy and security[4].

The OAuth 2.0 authorization framework relies on several key components to function. Access tokens represent specific scopes and durations of access, granted by the resource owner and enforced by both the resource server and authorization server[48]. Refresh tokens, which typically have longer lifespans than access tokens, allow applications to obtain new access tokens without requiring users to re-authenticate[15]. The authorization code flow, which is the most secure of the OAuth flows for traditional web and mobile applications, involves the authorization server returning an authorization code to the client after the user grants consent, which the client then exchanges for tokens through a back-channel request[58].

OAuth 2.0 introduced significant improvements over previous authentication methods by separating the roles of user authentication and application authorization. Rather than requiring users to share their passwords with third-party applications, OAuth allows applications to request access to specific scopes of data with user consent, and the authorization server issues tokens that represent that permission[4]. This delegation model has been widely adopted because it reduces credential exposure and allows fine-grained control over what access third parties receive.

However, the OAuth 2.0 specification as originally published contained security weaknesses that became apparent through years of real-world implementation and attack patterns. The original specification permitted several flows—including the implicit flow and resource owner password credentials flow—that created significant attack vectors[2]. The implicit flow, designed for browser-based applications, returned access tokens directly in the URL fragment, exposing them to interception through browser history, referrer headers, and other vectors[2]. Moreover, the original OAuth 2.0 specification explicitly stated that "authenticating resource owners to clients is out of scope for this specification," meaning that OAuth should not be used for authentication purposes without additional security mechanisms[2].

## Permission Leakage and Scope Creep Vulnerabilities

Despite OAuth 2.0's foundational design, a persistent and critical vulnerability has emerged around scope management and permission handling. OAuth scopes are designed to enforce the principle of least privilege, restricting applications to only the permissions they actually need[20]. In practice, however, scopes are often overly broad or completely static, creating what security researchers term "scope creep" and "overbroad permissions"[5][20]. A scope like `accounts.read` may expose all user accounts rather than only those the user intended to share[20]. Over time, as APIs evolve and scopes are reused across different applications, privilege creep sets in, with third-party apps retaining access to sensitive data they were never intended to access[20].

The problem is compounded by how tokens are requested and what permissions are granted during the OAuth flow. Many applications default to requesting the broadest possible access rather than limiting themselves to what they specifically need[5]. This creates a situation where seemingly harmless tools like a calendar app might be able to read, write, or delete emails, files, or contacts, simply because the application requested overly broad scopes and users accepted those requests without fully understanding the implications[5]. The lack of transparency in scope descriptions and the habitual nature of consent-clicking behavior means that excessive permissions often persist unexamined.

One of the least appreciated risks in OAuth workflows is the persistence of access tokens themselves[5]. Unlike passwords, which users might change regularly, OAuth tokens can remain valid for months or even years[5]. In some cases, unless explicitly revoked, they may never expire[5]. When an employee leaves a company or when a project ends, unless someone manually reviews and revokes those tokens, the third-party app can retain access to sensitive systems indefinitely[5]. These "zombie tokens"—forgotten, still-active authorizations that persist long after their intended use—represent an ongoing security liability that attackers actively seek out, knowing they are less likely to be monitored or deactivated[5].

Token leakage remains a persistent problem across the industry. OAuth tokens can be leaked in numerous ways, often without anyone noticing[5]. Debug logs, browser caches, clipboard history, or even GitHub repositories can inadvertently expose valid tokens[5]. Attackers actively search for these accidental disclosures using automated tools to scan public code and logs for secrets like API keys and OAuth tokens[5]. The challenge of token storage in single-page applications (SPAs) and mobile applications is particularly acute—these client-side applications cannot store tokens in HttpOnly+Secure cookies as server-side applications can[2]. Instead, they typically use sessionStorage or localStorage, both of which are accessible to attackers who find cross-site scripting (XSS) vulnerabilities[2].

Specific real-world incidents have demonstrated the severity of permission leakage risks in OAuth implementations. The UNC6040 Salesforce vishing campaign involved attackers using voice phishing to persuade users into authorizing a malicious Salesforce connected app with OAuth, leading to mass CRM data exfiltration[5]. The UNC6395 group exploited stolen OAuth tokens to target sensitive data across Salesforce, Google Workspace, and other business-critical SaaS platforms, bypassing MFA and gaining persistent access to organizations' most valuable data[5]. The Commvault supply-chain breach demonstrated how compromised OAuth tokens could grant MFA-bypassing access across environments through SaaS-to-SaaS compromise[5]. These incidents underscore that the vulnerability is not theoretical—attackers have systematically weaponized OAuth token management weaknesses to achieve their objectives.

The challenge extends beyond individual tokens to the broader question of scope governance. Many APIs do not validate the context in which a token is used[20]. If a token was issued to a specific IP address or app client, that metadata is rarely checked at runtime[20]. This opens the door to sophisticated replay attacks that mimic legitimate traffic with stolen tokens, allowing attackers to use compromised tokens as if they were the legitimate application[20]. Without context-aware access control, a stolen token represents full access to whatever the original token scope permitted, regardless of how that token is being used or where it is being used from.

## Interoperability Requirements and Their Security Implications

The drive to achieve interoperability across diverse banking systems introduces inherent complexities that can undermine security objectives. Standardization efforts aim to create uniform technical requirements that all participants must follow, but implementation variability remains a significant challenge. In Europe, despite PSD2's requirements for open banking APIs, individual banks have had considerable freedom to interpret API standards and mandates according to their own preferences, leading to insufficient uniformity across the industry[26]. This fragmentation means that rather than a single standardized approach, financial institutions must support multiple API standards—primarily STET, UK Open Banking, and XS2A in Europe—each with different technical implementations[26].

The requirement to support multiple standards and ensure compatibility across diverse platforms creates pressure to accept broader scope definitions and less restrictive permission models. When an API must serve many different types of clients—including web applications, mobile applications, internal systems, and third-party integrators—the temptation is to define scopes broadly enough to accommodate all anticipated use cases[8]. This approach prioritizes ease of integration over strict permission minimization, creating the conditions for scope creep.

Aggregators amplify these risks substantially. Third-party aggregators increase convenience for consumers by consolidating financial data from multiple sources, but they also multiply the risk surface[20]. When a single API endpoint serves multiple fintech applications, vulnerability is amplified across the ecosystem[20]. If an aggregator is compromised or behaves insecurely, every institution it connects to inherits that risk[20]. Many security leaders underestimate the risk of "secondhand exposure"—just because an open banking API is secure does not mean the entity consuming it is secure[20]. When aggregators chain multiple APIs together, tracing accountability becomes murky, with attackers thriving in these shadows[20].

The fundamental tension is that true interoperability requires standardization and openness, but security requires strict controls and careful governance. Each additional system integration, each new API connection, and each new third-party relationship increases the potential for permission mismanagement. The pressure to achieve the interoperability benefits of open banking—faster integration, broader access to financial services, lower barriers to innovation—can inadvertently push organizations toward security approaches that are more permissive than ideal.

## Vulnerabilities in OAuth 2.0 Implementation and Attack Vectors

Beyond scope creep, OAuth 2.0 implementations contain multiple well-documented vulnerabilities that enable attackers to steal authorization codes and access tokens. Perhaps the most infamous OAuth-based vulnerability occurs when the OAuth service itself enables attackers to steal authorization codes or access tokens associated with other users' accounts[25]. By stealing a valid code or token, an attacker may be able to access the victim's data and potentially log in as the victim user on any client application registered with the OAuth service[25].

One critical attack vector involves improper validation of redirect URIs. If the OAuth service fails to validate the redirect URI properly, an attacker may be able to construct a CSRF-like attack, tricking the victim's browser into initiating an OAuth flow that will send the code or token to an attacker-controlled endpoint[25]. In the case of the authorization code flow, an attacker can potentially steal the victim's code before it is used, then send this code to the client application's legitimate callback endpoint to get access to the user's account[25]. In this scenario, an attacker does not even need to know the client secret or the resulting access token[25].

Open redirect vulnerabilities represent another significant attack vector. An open redirect allows an attacker to use an authorization endpoint as a proxy to forward victims along with their code or token to an attacker-controlled domain where malicious scripts can be hosted[25]. This technique has been used effectively to steal authorization codes from victims, allowing attackers to complete the OAuth flow and gain account access. The severity of this attack is particularly high because the redirect occurs in the front-channel (through the victim's browser), making it difficult for users to detect that they are being redirected to a malicious site.

Flawed scope validation represents another important vulnerability category. In some OAuth implementations, it is possible for an attacker to "upgrade" an access token with extra permissions due to flawed validation by the OAuth service[25]. For example, an attacker's malicious client application might initially request access to a user's email address using the `openid email` scope[25]. After the user approves this request, the malicious client application receives an authorization code[25]. However, as the attacker controls their client application, they can add another scope parameter to the code/token exchange request containing additional scope values[25]. If the server does not validate this against the scope from the initial authorization request, it will sometimes generate an access token with the new, broader scope and send this to the attacker's client application[25].

The implicit flow, which was deprecated in OAuth 2.1, created particularly severe vulnerabilities. Because the entire implicit flow takes place through the browser, attackers who steal an access token can use it to make their own API calls to the resource server, potentially enabling them to fetch sensitive user data that cannot normally be accessed through the client application's web UI[25]. The implicit flow also exposed access tokens directly in the URL, making them vulnerable to interception through browser history, referrer headers, and other vectors[2].

## Modern Standards Evolution: FAPI 2.0 and OAuth 2.1

Recognizing the limitations and vulnerabilities of the original OAuth 2.0 specification, the financial services and technology communities have developed more stringent standards specifically designed for high-security scenarios. FAPI 2.0, an API security profile based on the OAuth 2.0 framework and suitable for protecting APIs in high-value scenarios[13][41], represents a significant advancement in open banking security. The Open Banking Standard has adopted FAPI 1 as its security profile, with FAPI 2.0 now available as an enhanced version[10].

FAPI 2.0 introduces several critical improvements over FAPI 1.0 that directly address token management and permission leakage concerns. Where FAPI 1.0 used JAR (JWT Authorization Request) for request integrity, FAPI 2.0 employs PAR (Pushed Authorization Request), which moves authorization request parameters out of the front channel to a back-channel submission, providing improved integrity protection and compatibility[16][41]. FAPI 1.0's JARM (JWT Authorization Response Mode) has been simplified in FAPI 2.0 to return only the authorization code in the response, eliminating the need for response integrity protection[16][41].

Most significantly, FAPI 2.0 makes Proof Key for Code Exchange (PKCE) mandatory for all clients, where FAPI 1.0 only recommended it[16][41]. PKCE prevents authorization code interception attacks by requiring clients to prove they possess a secret code verifier that matches the code challenge sent with the initial authorization request[55]. This mechanism ensures that even if an authorization code is intercepted, an attacker cannot redeem it without the corresponding code verifier[55]. The client generates a code verifier as a cryptographically random string, hashes it to create a code challenge, and sends the challenge with the authorization request[55]. When exchanging the code for tokens, the client sends the code verifier, and the authorization server validates that the hash of the provided verifier matches the originally submitted challenge[55].

FAPI 2.0 also strengthens sender-constrained token requirements. Whereas FAPI 1.0 specified Mutual TLS (mTLS) for certificate-bound access tokens, FAPI 2.0 allows either mTLS or DPoP (Demonstrating Proof-of-Possession), providing flexibility in implementation[16][41][27]. mTLS binds access tokens to specific client certificates at the transport layer, requiring that the same certificate used to obtain the token must be presented when using it[27]. DPoP operates at the application layer without requiring a public key infrastructure (PKI), instead using asymmetric cryptography and JSON Web Tokens to prove possession of a key[27]. Both approaches prevent stolen or leaked tokens from being used by unauthorized parties because possession of the token alone is insufficient—the attacker must also possess the corresponding cryptographic key or certificate.

Parallel to FAPI 2.0's development, OAuth 2.1 has consolidated best practices and removed dangerous flows from the OAuth specification entirely. OAuth 2.1 eliminates the implicit grant flow and the resource owner password credentials flow, removing the most dangerous attack vectors from the standard[28]. OAuth 2.1 prohibits tokens in query strings, requiring that access tokens appear exclusively in Authorization headers or POST request bodies[28]. This eliminates token leakage through browser history, referrer headers, and URL logging in various systems. OAuth 2.1 requires PKCE for all client types—confidential and public—whereas OAuth 2.0 only recommended it for public clients[28]. OAuth 2.1 requires exact string matching for redirect URI validation, eliminating the flexibility that attackers exploited through open redirect vulnerabilities[28]. OAuth 2.1 mandates refresh token rotation, where each time a refresh token is used, the server issues a new refresh token and immediately invalidates the old one[28], limiting the damage from token theft.

These standards improvements represent substantial advances in addressing token management vulnerabilities. However, their effectiveness depends entirely on implementation fidelity. Standards define what should be done, but implementation, governance, and ongoing management determine whether these protections actually function in practice.

## Third-Party Risk and the Liability Challenge

The open banking ecosystem introduces inherent risks through the participation of third-party providers who may not maintain security standards equivalent to regulated financial institutions. Third-party services have varying levels of security, and any vulnerability in third-party systems could potentially expose sensitive customer data[3]. Banks face a critical challenge: they must maintain security and integrity of customer data while granting access to third parties over whom they exercise limited direct control[3].

Before a third-party provider can access open banking APIs, they must first subscribe and undergo a rigorous verification process[3]. This process includes independent audits to validate that their systems and security controls meet required standards set by financial regulators and government bodies[3]. TPPs must demonstrate compliance with regional data protection laws like GDPR and international banking regulations like PSD2[3]. The onboarding process also ensures that TPPs maintain high standards of cybersecurity, have measures in place to detect and respond to security incidents, and commit to regular audits[3].

However, liability allocation under open banking regulations remains contested and unclear. PSD2 clarifies that account servicing payment service providers (ASPSPs) are fully liable for non-execution, defective execution, or late execution of payments, even where a payment initiation service provider (PISP) is involved[51]. ASPSPs must refund unauthorized transactions within one day unless there are reasonable grounds for suspecting user fraud[51]. Because ASPSPs are in control of which third parties they grant access to, they are liable for transactions initiated by those third parties[51]. However, the allocation of responsibility between ASPSPs and TPPs for security failures remains ambiguous, particularly when TPPs themselves prove to be untrustworthy or poorly secured[51].

This liability structure creates perverse incentives. Banks become the first point of responsibility, even when security failures occur at third-party providers. If a TPP has been revoked and cannot be contacted, there is nothing the ASPSP can do, but the bank still bears financial responsibility[51]. This has led some banks to argue that open banking imposes unfair liability structures, placing disproportionate responsibility on banks for security and API construction costs while limiting their ability to control their exposure[26].

The challenge intensifies when considering that banks must verify the regulatory status of TPPs to comply with PSD2's duty of care requirements[51]. Banks must conduct real-time verification of TPP regulatory status while avoiding creating obstacles to access, a balance that is difficult to achieve practically. The fundamental question becomes: how can an ASPSP ascertain a real-time process that sits seamlessly in their workflow without adding unacceptable friction?

## Data Minimization and Consent Management

Recognizing that permission leakage risks extend beyond technical token management to include the fundamental design of data-sharing relationships, modern open banking standards emphasize consent management and data minimization. Consent management is the process that enables users to authorize third parties to access and use their financial data while understanding who has access, specifying the duration and scope of access, and revoking consent at any time[14]. This customer-centric approach represents a philosophical commitment that users should control their data destiny[1].

The consent process in open banking typically begins when a customer interacts with a third-party provider offering financial services[14]. The TPP requests specific permissions—for example, access to account balances or transaction history[14]. The customer authenticates via their bank using Strong Customer Authentication (SCA)[14]. The customer then defines what data to share, for how long, and with whom, establishing what might be termed "granular access"[14]. Banks and TPPs provide dashboards for customers to track and manage active consents, and customers can revoke consent easily[14].

Strong Customer Authentication (SCA) has become a critical component of secure consent management. PSD2 requires that online payment transactions include two authentication factors, which can be based on knowledge (e.g., a password), possession (e.g., a card), or inherence (e.g., a fingerprint)[22]. SCA requirements help verify that the person granting consent is genuinely the account holder and that they understand what permissions they are granting. This reduces the risk that accounts are compromised through credential theft and then used to authorize excessive data sharing.

However, consent management faces practical challenges. Users often accept broad consent requests without understanding the implications, a phenomenon sometimes termed "consent fatigue" or "acceptance by habituation"[1]. When users are presented with consent screens that explain they are granting an application access to "read and write all account data," many users proceed without carefully considering whether the application truly requires such broad permissions. The responsibility for setting appropriate consent scopes therefore falls partially on application designers, who should limit scope requests to only what is necessary.

Regulators have increasingly emphasized data minimization as a core principle for open banking. Data minimization means that only the data necessary for a specified purpose should be collected and processed, with nothing beyond that required by the specific function[46]. This principle reflects the understanding that the amount of data shared directly correlates with the potential harm if that data is breached or misused. Applications should request access to account balances but not complete transaction history if only summary information is needed. Applications should request read access but not write access if only viewing data is required. Each reduced permission represents reduced risk.

## Implementation Challenges and Security Control Gaps

Despite the existence of well-designed standards like FAPI 2.0 and OAuth 2.1, implementation challenges and security control gaps persist throughout the industry. Many organizations have not yet adopted the newest standards, continuing to rely on earlier versions of OAuth 2.0 that lack modern security protections[28]. Even where newer standards are adopted, implementation inconsistencies create vulnerabilities. For example, some implementations may support PKCE but not require it, leaving the option of secure operation available but not mandatory[45]. Others may implement sender-constrained tokens through mTLS but fail to properly validate the certificate on every API call.

API security testing and governance often lag behind deployment timelines. Organizations frequently move APIs to production with incomplete security testing and inadequate governance structures[12]. Broken access control, which allows users to read or modify resources outside their intended scope, remains one of the most common API security vulnerabilities[12]. Poor authentication mechanisms and injection attacks round out the top security issues affecting APIs[12]. These fundamental vulnerabilities often reflect not advanced attack techniques but rather basic security control failures that could be prevented through proper design and testing.

The challenge of API inventory management directly impacts permission control. Development teams frequently deploy test APIs to production environments, creating additional security risks[12]. These forgotten, unused, or test APIs—called "shadow APIs" or "zombie APIs"—typically contain outdated code and lack current security controls[12]. In open banking environments, these shadow APIs can provide alternative access paths to financial data outside formal governance structures, enabling attackers to bypass primary security controls.

Rate limiting and resource constraints, while often implemented at the gateway level, may not be properly tuned for preventing abuse while maintaining legitimate access. Weak rate limiting invites brute force attacks, credential stuffing, and floods that probe business logic[9]. Financial institutions implementing open banking APIs must establish appropriate rate limits that prevent abuse without creating obstacles to authorized access. This balance is particularly challenging when aggregators legitimately need to make rapid, high-volume API calls to consolidate customer data from multiple sources.

Configuration weaknesses represent another critical gap. Many organizations set security configurations to defaults during development and forget to change them before production deployment[12]. CORS (Cross-Origin Resource Sharing) rules, for example, are often set to "allow all" during development and then never restricted to appropriate domains[12]. Default credentials and unnecessary API functionalities remain enabled because developers did not explicitly disable them. These configuration oversights, while often appearing trivial individually, create cumulative attack surfaces that sophisticated adversaries can exploit.

## Anomaly Detection and Real-Time Threat Response

Recognizing that static security controls are insufficient, modern open banking architectures increasingly incorporate anomaly detection and real-time threat response systems. These systems detect and respond to unusual activity that could indicate a security breach, using machine learning and other advanced analytics to monitor API traffic patterns and automatically flag activities that deviate from normal behavior[4][6]. Real-time monitoring tools track unusual activities that could indicate a breach, such as unusual API access patterns or unapproved API calls[4].

Machine learning-based anomaly detection systems can identify several categories of malicious behavior. Session hijacking can be detected through geographic anomalies or device shifts that suggest a different user is accessing an account[44]. Credential stuffing can be identified through repeated failed token exchanges[20]. Business logic abuse, such as excessively low-value payment requests that accumulate to larger fraud, can be detected through behavioral deviations[20]. When such anomalies are detected, systems can trigger additional authentication requirements, force re-authentication, or temporarily block access pending investigation.

However, anomaly detection systems have limitations. They require sufficient baseline data to establish what "normal" behavior looks like, making them less effective for newly opened accounts or unusual but legitimate use patterns. They generate false positives that must be investigated by security teams, creating alert fatigue if tuning is not careful. They operate reactively, detecting anomalies after they have occurred rather than preventing attacks before they begin. Most importantly, they require continuous investment in machine learning model refinement and threat intelligence integration to remain effective as attack patterns evolve.

The integration of anomaly detection with automated response mechanisms provides more robust protection. When anomalies are detected, automated systems can immediately impose rate limiting, force re-authentication, or even temporarily deactivate suspicious accounts pending human review[39]. These automated response mechanisms reduce the time window during which attackers can operate with compromised credentials or stolen tokens. However, automated systems risk blocking legitimate users if they flag normal but unusual activity (such as a customer accessing their account while traveling internationally).

## Zero Trust Architecture and Continuous Verification

Modern security architecture increasingly adopts zero trust principles, which are based on the concept of "never trust, always verify," refusing to automatically trust users even if they come from secure networks and have been verified[60]. In traditional banking security, perimeter-based security models locked the front door but left internal doors open—once authenticated, users received broad access[60]. Zero trust involves locking all internal doors and only granting access to authorized individuals, providing enhanced security and protection against internal network attacks[60].

In the context of open banking APIs, zero trust principles translate to requiring continuous verification of every access request, regardless of where it originates or what resource it accesses[6][11]. Authentication includes not just verifying identity through MFA or biometrics, but also employing behavioral analytics and context-based authentication that considers variables such as device health, location, and time of access[6][11]. This means that even if an access token is presented, the API gateway or resource server must verify that the token is being used in a context consistent with how it was issued.

The principle of least privilege access requires minimizing each user's exposure to sensitive parts of the network by granting users and devices only the minimum level of access necessary to perform their tasks[6][11]. This principle directly addresses permission leakage by ensuring that even if an access token is compromised, the damage is limited to whatever narrow access the token originally granted. Rather than issuing a single broad token that permits all operations, applications should use granular scoping where different operations require different tokens with different permission levels.

Segmentation divides the network into segments to reduce lateral movement within the network by attackers[6][11]. This creates micro-perimeters around sensitive data and systems, making it harder for an attacker to move through the network if they gain access through a compromised token or account. In the context of open banking APIs, this might mean restricting communication between a payment processing API and a customer onboarding API unless explicitly permitted, preventing an attacker who compromises one component from immediately accessing all others.

## Balancing Act: When Interoperability Pressures Compromise Security

The fundamental tension between interoperability and security becomes apparent when examining the evolution of open banking in different jurisdictions. The European Union's approach to standardization, for example, deliberately avoided mandating a single API standard, instead allowing banks to create their own data-sharing interfaces or participate in privately-led standardization initiatives[52]. This decision was based on the concern that a common API standard could hinder innovation and dynamic competition between standards[52]. However, the result has been insufficient uniformity, with European banks retaining considerable freedom to interpret API standards according to their preferences, leading to multiple incompatible implementations[26].

This fragmentation creates security compromises. When banks implement different API standards, third-party providers must support multiple versions, each with different security models. This complexity increases the likelihood of implementation errors and security oversights. The pressure to achieve interoperability with multiple standards encourages banks to define broader scopes and more permissive permission models than they would adopt if supporting a single standard. Each additional standard that must be supported represents additional complexity that security teams must validate and monitor.

The Australian experience with the Consumer Data Right provides an instructive contrast. Rather than leaving implementation to industry participants, the Australian approach included the requirement for each player to be licensed, ensuring compliance with data security and privacy safeguards[49]. Data is encrypted, and account aggregators cannot access or use the data for any other purpose[49]. This top-down solution with centralized enabling infrastructure and strict compliance requirements enforces security baselines across all participants.

In the United States, where open banking implementation remains largely voluntary and market-driven, implementation has been slower but more heterogeneous. Some large banks have proactively developed APIs and collaborated with fintech companies, while others have been slower to adopt[54]. This creates a fragmented landscape where the security of data depends heavily on the specific financial institution and third-party provider involved. Larger, more sophisticated institutions tend to implement stronger security controls, while smaller institutions may struggle to implement modern security architectures.

These divergent approaches illustrate a fundamental principle: standardization facilitates security by creating common baselines that all participants must meet, but it can also constrain innovation and competition. Market-driven approaches preserve innovation flexibility and competition but risk creating security gaps. The optimal solution likely involves standardized security requirements and testing, combined with flexibility in implementation approaches. Standards should mandate what security objectives must be achieved (authentication, encryption, access control) while remaining agnostic about specific technical implementations.

## Persistent Vulnerabilities in Real-World Implementations

Despite the evolution of standards and best practices, persistent vulnerabilities continue to affect open banking APIs in production environments. Insecure Direct Object Reference (IDOR) vulnerabilities allow attackers to access financial records by manipulating API parameters[9]. Attackers modify predictable identifiers to access other customers' transactions, statements, wire transfers, and loan applications[9]. This vulnerability reflects inadequate object-level authorization checks, where APIs fail to verify that authenticated users have permission to access the specific data they request.

SQL injection vulnerabilities remain surprisingly common in fintech API backends. Attackers inject SQL payloads through Authorization headers when APIs pass authentication data directly to database queries[9]. This technique has been used to extract sensitive customer data and compromise financial systems[9]. The continued prevalence of SQL injection reflects inadequate input validation and the error of passing authentication data directly to database queries rather than using parameterized queries and secure authentication frameworks.

Data exposure vulnerabilities occur when APIs return more data than necessary. This tends to cover database fields, debugging data, or system details in error messages[12]. Organizations often fail to define schemas for what each API should return, instead defaulting to returning entire data objects[12]. Responses should be trimmed of unnecessary details, and error messages should contain no system information[12]. The challenge is that this requires explicit design decisions by developers who may not fully appreciate the security implications of excessive data disclosure.

DDoS attacks and insufficient rate limiting have become common vectors for attacking fintech APIs. Hackers flood apps with traffic to crash them and force security breakdowns[9]. Many fintech APIs lack rate-limiting or resource restrictions required to fend off these attacks[9]. Without proper rate limiting, attackers can conduct credential stuffing attacks, brute force attacks against authentication mechanisms, or simple resource exhaustion attacks that degrade service quality for legitimate users.

Phishing remains a leading cause of data breaches, even in an era of strong authentication mechanisms[29]. Modern attacks feature attackers posing as banks or executives to trick users into sharing credentials[29]. Once inside, attackers introduce ransomware or cause massive data breaches[29]. Phishing against the employees and executives of open banking participants can be just as damaging as direct attacks on the APIs themselves, since compromised employee accounts may have elevated privileges and access to sensitive systems.

## Recommendations for Balanced Security and Interoperability

Achieving balance between security and interoperability requires a multi-faceted approach that addresses standardization, implementation, governance, and ongoing monitoring. Financial institutions and regulatory bodies should adopt the newest standards—FAPI 2.0 and OAuth 2.1—as mandatory baselines for new implementations and plan migration paths for legacy systems[10][28]. These newer standards incorporate lessons learned from years of real-world attacks and represent substantial security improvements over earlier versions.

Organizations should implement sender-constrained tokens using either mTLS or DPoP to prevent stolen or leaked tokens from being used by unauthorized parties[27]. This represents a critical control that limits the damage from token compromise. The choice between mTLS and DPoP should be based on organizational infrastructure and deployment context—mTLS provides strong security for confidential clients that can securely store certificates, while DPoP offers more flexibility for public clients and cloud-native environments.

API scope design should follow strict data minimization principles. Rather than defining broad scopes that cover entire data categories, organizations should define scopes that align with specific use cases[8]. A budgeting application should receive read-only access to transaction history but not write access or access to account settings. A payment initiation service should receive access to initiate payments but not to view transaction history or modify account details. These granular scope definitions reduce the blast radius if a token is compromised.

Comprehensive inventory management and governance of all APIs is essential[39]. Organizations should maintain real-time inventories of all active APIs, including their purposes, security controls, and connected systems[39]. Shadow APIs—undocumented endpoints that bypass security controls—should be actively sought out and either brought into governance frameworks or decommissioned[39]. API versioning policies should be clearly defined, with explicit sunset dates for deprecated versions[39]. Older API versions that cannot be adequately patched should be retired to eliminate time-bomb vulnerabilities.

Consent and permission management systems should provide transparency to users about what access they have granted and facilitate easy revocation[14]. Users should understand specifically what data is being shared, with whom, for what purpose, and for how long[14]. Permission revocation should be instantaneous and not require additional authentication or explanation[14]. Customer dashboards should show all active data-sharing relationships, allowing users to understand their privacy exposure at a glance.

Continuous monitoring and anomaly detection should be integrated with automated response mechanisms[6][20]. When suspicious behavior is detected—such as unusual data access patterns, geographic anomalies, or attempts to access data outside granted scopes—systems should automatically trigger additional verification or temporarily block access pending review[20]. This automated response capability dramatically reduces the time window during which attackers can operate with compromised credentials.

Third-party risk management must be robust and ongoing. Financial institutions should conduct comprehensive security assessments of third-party providers before granting API access and should maintain continuous monitoring of their security posture[37][40]. Contracts should include clear provisions for audit rights, access to security test results, and the ability to conduct on-site security reviews. Service level agreements should specify performance and security metrics, with consequences for failures[37][40].

## Conclusion

The evidence presented throughout this analysis demonstrates that open banking API standards do not fully achieve balance between data security and interoperability—instead, they represent ongoing negotiation between competing objectives, with implementation quality and governance determining the actual security outcomes. OAuth 2.0, while providing significant improvements over screen scraping and proprietary APIs, contains inherent vulnerabilities around token management, scope creep, and permission persistence that create material risks of permission leakage. These vulnerabilities are not mere theoretical concerns; they have been systematically exploited by sophisticated threat actors to compromise financial systems and exfiltrate customer data at scale.

Modern standards improvements—particularly FAPI 2.0 and OAuth 2.1—represent substantial progress in addressing these vulnerabilities. Mandatory PKCE usage, sender-constrained tokens through mTLS or DPoP, and the elimination of dangerous flows have genuinely improved security postures compared to earlier implementations. However, these improvements are only effective when implemented with fidelity and maintained through ongoing governance. The gap between the security level achievable by standards and the security level actually achieved in practice remains substantial, driven by implementation challenges, configuration errors, scope governance failures, and inadequate ongoing monitoring.

The interoperability objectives of open banking are legitimate and valuable. Standardized APIs do enable innovation, lower barriers to entry for fintechs, improve customer choice, and reduce friction in financial services. However, these benefits should not be achieved by accepting unmanaged security risks. Rather, standardized security requirements should be treated as non-negotiable prerequisites for participation in open banking ecosystems. Just as financial institutions must meet capital adequacy requirements and anti-money laundering standards to participate in banking, they should be required to meet standardized security baselines for open banking participation.

Ultimately, the question posed in this query—whether open banking standards balance security and interoperability or whether OAuth 2.0 token management increases permission leakage risks—has a nuanced answer. Standards provide the framework for achieving balance, but actual outcomes depend on implementation, governance, and ongoing management. Organizations that implement modern standards, follow security best practices, invest in comprehensive monitoring and detection capabilities, and maintain rigorous governance over permissions and access can achieve open banking ecosystems that are both interoperable and secure. Organizations that treat security as an afterthought to interoperability will inevitably experience permission leakage, token compromise, and data breaches. The choice lies with implementation teams, security leaders, and regulators who must insist that security baselines are not negotiable even as they pursue interoperability benefits.
