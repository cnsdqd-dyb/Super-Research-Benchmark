In practice, financial consortia almost always avoid heavy proof-of-work or ZK schemes and instead use Byzantine-fault-tolerant (BFT) or authority‐based consensus.  In a permissioned setting the validator set is known, so consensus can be reached by digital signatures and voting rounds rather than expensive proofs.  For example, many enterprise chains use PBFT‐style protocols (Practical Byzantine Fault Tolerance) or derivatives (Istanbul BFT, HotStuff, Tendermint, etc.).  These algorithms give *immediate finality* (no forks) and tolerate up to ~1/3 faulty nodes, yet each block only needs a small number of signed messages.  In fact, IBFT (used in private Ethereum/Quorum) “reduces the work needed to construct and validate blocks … greatly increasing throughput” compared to PoW ([consensys.io](https://consensys.io/blog/scaling-consensus-for-enterprise-explaining-the-ibft-algorithm#:~:text=IBFT%20is%20one%20of%20the,and%20provides%20the%20following%20benefits)).  Likewise, pBFT guarantees finality – a block agreed by the supermajority can never be reverted ([www.halborn.com](https://www.halborn.com/blog/post/what-is-practical-byzantine-fault-tolerance-in-blockchain#:~:text=,of%20nodes%20cannot%20be%20reverted)) – and operates with very low per-node computation (just hashing and signing).

The key point is that these BFT protocols rely on conventional cryptography (ECDSA signatures, etc.) and a fixed set of validators, not on heavy zero-knowledge proofs.  Because the participants are trusted organizations, there is no need for anonymous privacy proofs at the consensus layer.  Eliminating proof-of-work (or ZK) means blocks can be produced and signed in milliseconds, yielding very high throughput.  In practice, PBFT‐style systems routinely handle thousands of transactions per second on networks of a few dozen nodes ([consensys.io](https://consensys.io/blog/scaling-consensus-for-enterprise-explaining-the-ibft-algorithm#:~:text=IBFT%20is%20one%20of%20the,and%20provides%20the%20following%20benefits)) ([www.halborn.com](https://www.halborn.com/blog/post/what-is-practical-byzantine-fault-tolerance-in-blockchain#:~:text=,of%20nodes%20cannot%20be%20reverted)).  For example, Tendermint (Cosmos) and Algorand’s Pure PoS consensus use similar ideas of validator committees and have demonstrated high TPS in live networks without any ZK computation.

Of course, classic PBFT does incur O(n²) messaging, so scaling beyond a few dozen nodes requires some tweaks.  Recent research shows how to extend BFT consensus to larger consortiums.  One approach is **sharding or hierarchical BFT**: partition the alliance into sub-committees and run parallel consensus in each shard.  For instance, the KBFT protocol “shards the nodes into clusters” and reaches consensus on disjoint transactions in parallel, using a lightweight proxy/credit system to maintain security ([www.nature.com](https://www.nature.com/articles/s41598-022-27228-1#:~:text=The%20consensus%20algorithm%20is%20very,The%20KBFT%20algorithm)) ([www.nature.com](https://www.nature.com/articles/s41598-022-27228-1#:~:text=first%20uses%20the%20K,show%20that%20the%20proposed%20algorithm)).  Another proposal (tPBFT) uses a trust‐score mechanism to select a smaller active validator set, reducing communication overhead and dramatically improving throughput as nodes grow beyond ~30 ([www.nature.com](https://www.nature.com/articles/s41598-022-08587-1#:~:text=paper%20proposes%20an%20improved%20algorithm,of%20nodes%2C%20the%20improved%20tPBFT)).  In short, by combining BFT voting with leader rotation, sharding or committee selection, consortium chains can scale out while still enjoying low latency and finality.

In summary, yes – consortium blockchains almost universally use BFT or authority‐based consensus rather than ZK.  Protocols like PBFT/IBFT (and their modern variants) achieve strong security (Byzantine fault tolerance and instant finality) and very high throughput by having a small, vetted set of validators sign off on each block ([consensys.io](https://consensys.io/blog/scaling-consensus-for-enterprise-explaining-the-ibft-algorithm#:~:text=IBFT%20is%20one%20of%20the,and%20provides%20the%20following%20benefits)) ([www.halborn.com](https://www.halborn.com/blog/post/what-is-practical-byzantine-fault-tolerance-in-blockchain#:~:text=,of%20nodes%20cannot%20be%20reverted)).  This avoids the heavy computation of ZK proofs entirely while still meeting the security/throughput needs of a financial alliance.
