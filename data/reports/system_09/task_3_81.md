In practice, the “hierarchy” of API permissions in third‐party access schemes is set by the resource owner’s own privileges, as mediated through the OAuth/OpenID Connect model of scopes.  In other words, a user (the resource owner) has a certain set of rights, and any third‐party app can only act on a strict subset of those rights.  OAuth 2.0, for example, defines *scopes* that a user consents to grant a client – and these scopes **only limit** the client’s access, never expand it beyond the user’s privileges.  As an Auth0 security post explains, “scopes… always limit what an app can do on behalf of a user: a scope cannot allow an application to do more than what the user can do” ([auth0.com](https://auth0.com/blog/on-the-nature-of-oauth2-scopes/#:~:text=TL%3BDR%3A%20Scopes%20only%20come%20into,what%20the%20user%20can%20do)).  In short, the resource owner’s privileges are at the top of the hierarchy, and the granted OAuth scopes merely narrow those privileges for the third party ([stackoverflow.com](https://stackoverflow.com/questions/48351332/oauth-scopes-and-application-roles-permissions#:~:text=OAuth%202,user%20has%20the%20corresponding%20privilege)) ([auth0.com](https://auth0.com/blog/on-the-nature-of-oauth2-scopes/#:~:text=TL%3BDR%3A%20Scopes%20only%20come%20into,what%20the%20user%20can%20do)). 

**Sources:** OAuth 2.0 (RFC 6749) and related standards; see e.g. Auth0 on OAuth scopes ([auth0.com](https://auth0.com/blog/on-the-nature-of-oauth2-scopes/#:~:text=TL%3BDR%3A%20Scopes%20only%20come%20into,what%20the%20user%20can%20do)) and StackOverflow discussion ([stackoverflow.com](https://stackoverflow.com/questions/48351332/oauth-scopes-and-application-roles-permissions#:~:text=OAuth%202,user%20has%20the%20corresponding%20privilege)).
