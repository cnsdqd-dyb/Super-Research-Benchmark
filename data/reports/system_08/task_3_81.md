# Third-Party API Access and Permission Hierarchy

**Third-party API access** allows external applications or services to interact with a platform’s API on a user’s behalf — for example, when you let a mobile app access your cloud drive or social media account. To ensure security and privacy, this access is *limited by a permission hierarchy*. In other words, the third-party app doesn’t get free rein over your data; it only gets the specific permissions that have been authorized. This hierarchy of permissions is established by widely adopted **authorization standards** that dictate how and what access is granted.

## OAuth 2.0 and Scopes as the Foundation

One of the most common standards for third-party API access is **OAuth 2.0**, an authorization framework used by providers like Google, Facebook, and Microsoft ([en.wikipedia.org](https://en.wikipedia.org/wiki/OAuth#:~:text=OAuth%20,party%20applications%20or%20websites)). OAuth 2.0 issues **access tokens** to third-party clients with a defined set of permissions, rather than sharing user passwords ([en.wikipedia.org](https://en.wikipedia.org/wiki/OAuth#:~:text=client%20application%20%20with%20secure,hosted%20by%20the%20resource%20server)). The key mechanism OAuth uses to establish a permission hierarchy is the concept of **scopes**. 

- **Scopes as Permission Levels:** *Scopes* are essentially labels for specific permission sets or API capabilities. Each scope corresponds to a certain level or category of access. For example, an API might define separate scopes for *read-only access* versus *write access* (e.g. `read_profile` vs. `edit_profile`), or basic profile info versus sensitive data. When a third-party app requests access, it specifies which scopes it needs. These scopes create a layered model of permissions — a hierarchy from less sensitive actions (like reading data) up to more sensitive actions (like modifying or deleting data).

- **User Consent:** Critically, the **user (resource owner)** must approve the scopes an application requests. During the OAuth flow, the user is shown a consent screen listing the requested scopes (e.g. “This app wants permission to *read your contacts*”). The user can then grant or deny access. Only the approved scopes become attached to the issued access token. In this way, *user consent paired with scopes defines the effective permission hierarchy* for the third-party: the app is constrained to the actions the user agreed to. As one guide puts it, OAuth scopes “allow your users to grant permission to data held by you to third-party applications” ([fusionauth.io](https://fusionauth.io/blog/how-to-design-oauth-scopes#:~:text=OAuth%20scopes%20allow%20your%20users,become%20more%20and%20more%20critical)), effectively creating **groups of permissions** that a user can allow or deny for the app ([fusionauth.io](https://fusionauth.io/blog/how-to-design-oauth-scopes#:~:text=Scopes%20are%20fundamentally%20a%20way,or%20deny%20to%20an%20application)).

- **Enforcement via Access Tokens:** Once the token is issued with specific scopes, the **API (resource server)** enforces those permissions. Every incoming API call from the third-party app carries the access token, and the server checks the token’s scopes. If the app tries an operation outside its scoped permissions, the request is rejected. For instance, an access token with only a “read” scope will be refused if it attempts a “write” operation. In this way, scopes in the token act as a *clear hierarchy of what the app can do*, and the API’s enforcement ensures the third-party stays within those bounds ([en.wikipedia.org](https://en.wikipedia.org/wiki/OAuth#:~:text=limited%20in%20granularity%20to%20the,policies%20that%20work%20on%20the)).

## Granular Hierarchy: Roles and Advanced Controls

Basic OAuth scopes provide **coarse-grained** permission control – they cover broad functional areas (read, write, etc.) of the service ([en.wikipedia.org](https://en.wikipedia.org/wiki/OAuth#:~:text=XACML%20provides%20more%20fine,the%20applications%2C%20processes%2C%20and%20data)). Many APIs keep things simple with just a few scopes, but others implement a more granular hierarchy on top of OAuth:

- **Fine-Grained Scopes:** Some services offer many specific scopes so that third-party access can be tightly limited. For example, a banking API might have separate scopes for reading account balances, initiating payments, or viewing transaction history, rather than a single “full access” scope. The more fine-grained the scopes, the more precisely the permission hierarchy can match real-world least-privilege needs (though very granular scopes also increase complexity).

- **Role-Based Access Control (RBAC):** In addition to or instead of multiple scopes, an API may use roles or permission tiers. In an RBAC model, the third-party application could be granted a **role** (e.g. “Viewer” vs “Editor” vs “Admin”), and each role encompasses certain permissions. This is common in enterprise or partner APIs. In OAuth terms, roles can be conveyed as part of the token (for instance, in a JWT access token, there might be a claim listing user roles or privileges). While OAuth itself doesn’t define roles, the **authorization server** or identity provider can include roles/claims in tokens, and the API uses those to determine access. Essentially, roles create a hierarchy (admin > user > guest, etc.) that the API recognizes, supplementing the scope mechanism.

- **Attribute-Based and Policy-Based Controls:** Some advanced standards like **XACML** or **User-Managed Access (UMA)** extend the idea of permission hierarchy even further. They allow fine-grained policies based on attributes and user-defined rules. For instance, XACML policies might say *“Managers can view any document in their department”* – a rule that goes beyond simple scopes ([en.wikipedia.org](https://en.wikipedia.org/wiki/OAuth#:~:text=Where%20OAuth%20focuses%20on%20delegated,they%20own%20in%20draft%20mode)). These aren’t as universally adopted as OAuth, but in certain domains they establish a detailed hierarchy of who can access what. In practice, OAuth’s scopes are often combined with such policy engines to achieve both broad **delegated access** control and detailed permission governance ([en.wikipedia.org](https://en.wikipedia.org/wiki/OAuth#:~:text=XACML%20provides%20more%20fine,the%20applications%2C%20processes%2C%20and%20data)).

## Putting It All Together

In **third-party access standards**, the API permission hierarchy is primarily established by the **authorization framework and its permission definitions**. OAuth 2.0 (often with OpenID Connect for identity) is the de facto standard; it introduces **scopes** as the building blocks of permissions and relies on user consent to grant just the needed scope levels to third-party apps. The API provider predetermines these scopes (and/or roles) to map to different access levels, effectively creating a structured hierarchy from minimal access up to full control. 

This means a third-party integration is **safely constrained**: it operates within the permission tier it has obtained. A well-designed API will expose multiple scopes or roles so that an app can be given the *least privilege* it requires rather than a blanket all-access key. In summary, **scopes and related mechanisms (like roles)** are what establish and enforce the API permission hierarchy in modern third-party access standards, ensuring that external apps only touch what they are authorized to, and nothing more ([fusionauth.io](https://fusionauth.io/blog/how-to-design-oauth-scopes#:~:text=Scopes%20are%20fundamentally%20a%20way,or%20deny%20to%20an%20application)) ([en.wikipedia.org](https://en.wikipedia.org/wiki/OAuth#:~:text=XACML%20provides%20more%20fine,the%20applications%2C%20processes%2C%20and%20data)).
